>
> 保留价值仅在于追溯当时的观察与推理过程。修复后的对照数据见
> `archive/runs/` 下 `*_engine1.0.0_*.tev.json`（引擎 1.0.0 + 格式版本 1）。

> 
> **关于本报告的性质**：它记录的注入规模敏感性、混沌性等观测**是在缺陷引擎上取得的**，数据本身不可信。但它的主要作用是**定位并量化那个缺陷本身**（席位累积到 171%、根因定位到按编码聚合的配额表），这一部分结论依然成立，且是修复的依据。文中的「实验 A/B」具体数值不应引用。

# 实验报告：R1-1 注入的扩散能力、行为等价性，以及一个引擎级 Bug

- 基础 seed：`3238503071158768080`（默认初始条件，已验证 G0 与原报告一致：`F2-3+R2-3+H3-2+C2-D` = 23 席）
- 注入时点：G241（与原报告一致）
- 全部实验用项目内 `TrustEvolution` / `inject_strategy` / `step()`，无外部近似
- 单次 330 代耗时约 30 秒

## 零、先说最重要的：发现引擎 Bug

在复现原报告时发现 **`reproduce()` 存在累积性席位泄漏**，见第五节。
**在此 Bug 修复前，下面所有"份额/规模"数字都应视为可疑。**

## 一、实验 A：注入 `R1-1` + `SM`（永远背叛）

| 臂 | 注入 | 终局状态 | R1-1 家族合计 | SM 存活 |
|---|---|---|---|---|
| A1 | `R1-1`(20) | `R1-1`=67, `R2-1`=33（2 物种） | **100 / 100** | — |
| A2 | `R1-1`(20) + `SM`(20) | `R1-1`=53, `R1-1+M2`=27, `R2-1`=7, `R3-1`=7, `R2-1+RPTM-3`=4（5 物种） | **98 / 100** | **0** |

**结论**
1. **`SM` 被彻底清零**——预测成立。纯背叛者在有报复者的生态里无法立足。
2. **R1-1 家族的生态级统治不受 SM 影响**（100 → 98）。
3. **但内部构成明显改变**：A1 只有 2 个物种，A2 变成 5 个，并**新演化出 `M2`（健忘）、`RPTM-3`（宽容）模块**。

> 这直接回应"等价策略"问题：
> **在"谁统治生态"这一层等价；在"哪些变体留存"这一层不等价。**
> 加入一个持续背叛者会改变选择压，从而让原本"看不见"的模块差异（宽容/健忘）显形。
> 所以"R1-1 等价策略"应表述为：**生态位等价，而非行为等价。**

## 二、注入规模的敏感性扫描（`R1-1`，G241 注入）

| 注入规模 | 终局最大物种 | 终局物种数 | R1-1 自身席位 |
|---|---|---|---|
| 10 | `R1-1`=48 | 3 | 48 |
| 15 | `R1-1`=63 | 5 | 63 |
| 20 | `R1-1`=67 | 2 | 67 |
| 25 | `BS1+RC1-1+C3`=17（**`R1-1` 掉到 17**） | **10** | 17 |
| 30 | `R1-1`=74 | 3 | 74 |
| 35 | `R1-1+M2`=19（`R1-1`=16） | 7 | 16 |
| **40** | **`R1-1`=100（独占）** | **1** | 100 |
| **45** | `BS1+H2-3+B1-2+RPT1-1`=39（**击败 `R1-1`=34**） | 4 | 34 |
| 50 | `R1-1`=68 | 2 | 68 |

**结论：响应是非单调、强混沌的。**
- 规模 20 → 家族 100%；规模 **25 → `R1-1` 被压到 17 席、生态裂成 10 个物种**；规模 40 → 独占 100%；规模 **45 → 被一个完全不同的策略击败**。
- 这意味着**"R1-1 有强大扩散能力"不是一个稳健结论**，而是"在某些注入规模下成立"的结论。
- 注入规模 25 与 20 只差 5 席，结果却从"完全统治"变成"被压制"——这是典型的混沌敏感性。

| 臂 | 终局 |
|---|---|
| 无注入，G330 | `F1-3+R2-3+H3-2+C2-D`=**80** / 100（5 物种） |

## 四、复现失败说明

原报告终局为 `R1-1`=47 / `R2-1`=22 / `R1-1+RPTM-M`=21 / `D0+B1-3+C4-C`=8 / `R3-1`=1。
从 G241 行读出 `R1-1` 注入规模 = **10**（原报告 G241 行 `R1-1` 列 = 10）。

用规模 10 复现得到 `R1-1`=48 / `R2-1`=23 / `R1-1+RPTM-M`=21 —— **前两项各差 1 席，且原报告多出 9 席的两个小物种**，说明复现轨迹在注入后不久发生轻微分叉。
最可能的原因：`re_record_frontier()` 会重跑 `_current_evaluation()`，**额外消耗 RNG**，使后续所有代数的随机流发生偏移（详见第五节 Bug D）。
结论：**原报告的精确构成无法用脚本复现**，但"注入 `R1-1` 后其家族取得支配地位"这一现象在所有注入规模下都能复现（除 25/45 两个反例）。

## 五、引擎 Bug：`reproduce()` 席位泄漏

### 现象

同一次运行中，逐代检查 `sum(species.total_size)`：

| 代数 | 物种数 | 席位合计 | 超出容量 | 重复编码 |
|---|---|---|---|---|
| 0 | 7 | 100 | 0 | - |
| 40 | 2 | 100 | 0 | - |
| 60 | 7 | **109** | +9 | `F3-3+R2-3+H3-2+C2-D`×2, `F1-3+R2-3+H3-2+C2-D`×2 |
| 140 | 8 | 117 | +17 | 同上 |
| 220 | 10 | 143 | +43 | 同上 |
| 240 | 7 | **171** | **+71** | 同上 |

从约 G57 起，`sim.species` 中出现**编码完全相同的多个 `Species` 对象**，且**总席位单调增长到容量的 171%**。

### 根因

`trust_evolution_simulation.py:554-567`：

```python
def reproduce(self) -> None:
    total = sum(item.total_size for item in self.species)
    if total == 0:
        return
    if total != TOTAL_CAPACITY:
        scales = {
            item.encoding: item.population_size * TOTAL_CAPACITY / total   # ← 字典按编码聚合
            for item in self.species
        }
        allocation = _round_robin_sizes(scales, max(TOTAL_CAPACITY - sum(
            item.subspecies.size if item.subspecies else 0 for item in self.species
        ), 0))
        for item in self.species:
            item.population_size = allocation[item.encoding]               # ← 两个重复编码拿到同一份配额
```

- `scales` / `allocation` 是**以 `encoding` 为键的字典**。
- 当一个亚种变异回**已存在的策略编码**并独立（`mutate_and_evolve_subspecies()` 第 682-693 行 `self.species.append(new_species)`）时，`sim.species` 里就出现两个同编码对象。
- 字典把二者**合并成一个键**，随后 `for item in self.species: item.population_size = allocation[item.encoding]` 让**两个对象拿到同一份配额** → 该编码席位翻倍。
- 由于 `total != TOTAL_CAPACITY` 每代都会触发重整，这个翻倍**逐代复利累积**，最终 +71 席。

### 连带影响（比 Bug 本身更严重）

| 影响 | 说明 |
|---|---|
| **报告与面板population 少报** | `_record_generation()` 的 `species_data` 也是按编码聚合的字典，重复编码被静默覆盖。原报告 G240 行合计恰好 100，而真实状态是 171 |
| **所有"份额/占比"结论失真** | 分母偏小 → 头部物种份额被高估、生态多样性被低估 |
| **注入归一化失效** | `inject_strategy()` 依赖 `total_size` 求和做等比缩放，泄漏会污染缩放系数 |
| **注入行记录异常** | 原报告 G241 行合计仅 62（`re_record_frontier` 重录所致），同样源于该聚合不一致 |

### 附带发现（次要）

- `reproduce()` 的缩放基数不一致：`scales` 用 `population_size * CAPACITY / total`（`total` 含亚种），而目标容量用 `CAPACITY - sum(亚种)`，两者基准不同，会引入额外漂移。
- `re_record_frontier()` 重跑 `_current_evaluation()` 消耗 RNG，是复现分叉的嫌疑来源。

## 六、建议的修复顺序

1. **修 `reproduce()`**：把 `scales` / `allocation` 改为按**对象**（或索引）而非按编码聚合；重复编码应视为同一物种并**合并席位**。
2. **在独立化时去重**：`mutate_and_evolve_subspecies()` 第 693 行 append 前，先检查 `child.encoding` 是否已存在；存在则把席位并入既有物种（记 `subspecies_independent` 事件），不再新建 `Species`。
3. **加容量断言**：每代 `step()` 末尾断言 `sum(total_size) == TOTAL_CAPACITY`，让泄漏立即暴露而不是静默累积。
4. **修 `_record_generation()`**：同编码合并而非覆盖，避免报告少报。
5. **修 `re_record_frontier()`**：不要为重录而重新评估（避免 RNG 消耗），直接用现有 `fitness`/`matchup` 重写记录。
6. 修完后**重跑三份存档的 seed**，此前所有"份额"结论需重新核对。
